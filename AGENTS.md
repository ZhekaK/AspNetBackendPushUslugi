# Памятка по проекту PushPelmesh

Этот файл — карта репозитория для следующего чата/агента. Перед изменениями сверяйте детали с текущим кодом: описанное здесь состояние относится к ревизии, изученной 7 октября 2026 года. Пишите пользователю по-русски.

## Что это

`PushPelmesh.sln` содержит один серверный проект `PushPelmesh.Api` — ASP.NET Core Minimal API на .NET 10. Приложение хранит данные в PostgreSQL через Entity Framework Core/Npgsql, выдаёт JWT, поддерживает Web Push и прикладные модули «Пыш-Услуг»: аккаунты/удостоверения и должности, календарь, уведомления, награды, кино, голосования, сохранения Xoxi, игры Zong и «Дурак». Отдельного фронтенд-проекта и тестового проекта в репозитории нет.

## Запуск и проверка

- Нужны .NET SDK 10 и доступная PostgreSQL. Целевая платформа — `net10.0`; основные NuGet-пакеты: EF Core/Npgsql, JWT Bearer, Swashbuckle, WebPush.
- Локальные `PushPelmesh.Api/appsettings.json` и `appsettings.Development.json` исключены из Git. Для запуска задайте `ConnectionStrings:DefaultConnection`, `Jwt:Key`, `Jwt:Issuer`, `Jwt:Audience`, `Admin:Key`; для реальной отправки Web Push также `Vapid:PublicKey`, `Vapid:PrivateKey`, `Vapid:Subject`. Не записывайте реальные секреты в этот файл или Git. Настройки можно передать стандартным механизмом конфигурации ASP.NET Core, например переменными окружения с `__` вместо `:`.
- `dotnet build PushPelmesh.sln` — базовая проверка компиляции. На момент создания этой памятки `dotnet build PushPelmesh.sln --no-restore` прошёл без ошибок и предупреждений.
- `dotnet run --project PushPelmesh.Api --launch-profile http` запускает локальный профиль на `http://localhost:5028`; HTTPS-профиль использует `https://localhost:7039` и HTTP-порт 5028. Swagger UI доступен только в `Development` по `/swagger`; простой маршрут проверки — `GET /api/ping`.
- **Запуск вызывает `db.Database.Migrate()` до настройки маршрутов.** Убедитесь, что строка подключения указывает на нужную БД; запуск может изменить её схему. Новые изменения сущностей и `AppDbContext` сопровождайте новой миграцией EF Core, затем проверяйте сборку и запуск на подходящей тестовой БД.
- Автоматизированных тестов, Dockerfile и CI-конфигурации в репозитории на момент описания нет. Не выдавайте успешную сборку за проверку работы с БД, HTTP или отправки push.

## Доступ и пользователи

- `POST /api/auth/login-by-key` ищет `AccessKey` по серии и номеру, активирует его при первом входе, создаёт/обновляет пользователя и выдаёт JWT. `POST /api/auth/guest` создаёт гостя и тоже выдаёт JWT. JWT живёт 7 дней; в нём `NameIdentifier` = ID пользователя, `Name` = имя, `Role` = строковое значение `UserType`.
- Для негостевого входа по ключу ответ содержит `rememberToken`: случайный секрет устройства, SHA-256 которого хранится в `RememberedLogins`. После истечения JWT клиент вызывает `POST /api/auth/login-by-name` с этим секретом и `firstName`. Три неверных имени удаляют запись устройства и требуют входа по ключу. Не реализуйте вход по одному только имени без секрета устройства.
- `UserType`: `Guest`, `KeyUser`, `Admin`. Должности хранятся отдельно в `UserRole` (`None`, `Minister`, `Governor`, `President`) и связываются с пользователем по `UserSeries` + `UserNumber`, а не по внешнему ключу. При работе с полномочиями смотрите конкретный маршрут: одной только JWT-роли недостаточно для выводов о должности.
- Обычные защищённые маршруты используют `.RequireAuthorization()` и `Authorization: Bearer <token>`. Административные маршруты вручную вызывают `AdminKeyValidator.IsValid()` и ждут `X-Admin-Key`, равный `Admin:Key`; это отдельный механизм, не требующий JWT в текущем коде. Проверяйте каждый новый маршрут явно — общего admin route group нет.
- `GET /api/user/me`, `GET /api/user/profile`, `PUT /api/user/profile/weight` работают с текущим пользователем. Запрос профиля обновляет `LastLoginAt`; вес допускается в интервале `(0, 500]` кг.

## Карта API по модулям

Все пути ниже указаны относительно сервера. Точные поля и коды ответов смотрите в соответствующем endpoint-файле и DTO.

| Модуль | Основные маршруты и особенности |
| --- | --- |
| Администрирование | `GET /api/keys`, `POST /api/admin/keys/generate`, `POST /api/admin/keys/activate-all`; `GET /api/admin/users`; `GET /api/admin/roles`, `POST /api/admin/roles/generate`, `POST /api/admin/roles/remove`, `DELETE /api/admin/roles/{id}`; `DELETE /api/admin/cleanup-guests` (гости с `LastLoginAt` старше 7 дней). Все эти маршруты проверяют `X-Admin-Key`. |
| Профиль и должности | `GET /api/user/me`, `/api/user/profile`, `/api/user/role`; `PUT /api/user/profile/weight`. Должности пользователя выбираются по серии/номеру. |
| Xoxi | `GET`/`PUT /api/xoxi/save`: один произвольный JSON-объект сохранения на пользователя, колонка `jsonb` в таблице `xoxi_saves`. |
| Календарь | `GET /api/calendar/events?from=&to=`, `POST /api/calendar/events`, `DELETE /api/calendar/events/{id}`. Создавать события может президент, а министр — встречи; удалять обычное событие может автор, `Admin` или президент. Системные события через этот DELETE не удаляются. Админские `POST /api/admin/calendar/sync-birthdays` и `/refresh-birthdays` используют admin key. |
| Уведомления | `POST /api/push/subscribe` и `/unsubscribe`; `GET /api/module-notifications/unread`, `POST /api/module-notifications/{moduleKey}/read`. `POST /api/admin/push/system` отправляет системный Web Push всем негостевым или указанным по серии/номеру пользователям и требует admin key. |
| Награды | `GET /api/rewards/championships`, `/government-awards` требуют JWT; `POST /api/admin/rewards` требует admin key. Награду можно связать с пользователем по серии/номеру либо сохранить с указанным полным именем. |
| Кино | `GET`/`POST /api/cinema/movies`: просмотр списка и добавление фильма с рейтингом, датой просмотра, URL и флагом `isExtra`. Требуют JWT. |
| Мессенджер | `/api/messenger/users`, `/chats`, `/chats/direct`, `/chats/group`, `/chats/{id}/messages`, `/chats/{id}/mute`, `/chats/{id}/read`. Общий чат имеет виртуальный ID `0`; прямые и групповые чаты хранятся в `ChatRooms`, участники в `ChatParticipants`, сообщения в `ChatMessages`. `ChatNotificationSettings` хранит отдельную для пользователя и чата настройку звука и ID последнего прочитанного сообщения; `GET /chats` возвращает `muted` и `unread`. Новое сообщение отправляет Web Push немьютированным участникам с подпиской. Доступ только у негостевых пользователей с серией и номером ID; чтение, отправка и настройка личного/группового чата разрешены только участникам. |
| Голосования | `GET /api/votes/polls`, `GET /api/votes/polls/{id}`, `POST /api/votes/polls`, `POST /api/votes/polls/{id}/vote`. Требуют JWT. Опросы бывают с одним или несколькими вариантами; доступ ограничивается флагами аудитории `RegularUsers`/`Ministers`, при этом `Admin`, президент и губернатор видят все. Создание опроса формирует модульные уведомления и Web Push; закрытие определяется датой по Москве. |
| Zong | `GET`/`POST /api/zong/rooms`, `POST /api/zong/rooms/{id}/join`, `GET /api/zong/rooms/{id}`, `POST .../start`, `.../roll`, `.../bank`. Это пошаговая игра с кубиками, комнатой на 2–8 игроков, целью по очкам и опциональным паролем. |
| «Дурак» | `GET`/`POST /api/durak/rooms`, `POST .../{id}/join`, `GET .../{id}`, `POST .../{id}/start`, `.../attack`, `.../defend`, `.../transfer`, `.../take`, `.../pass`. Сервер хранит колоду, стол и руки игроков в `jsonb`, а DTO возвращает клиенту только его руку. Правила ходов и переходов находятся в `DurakEndpoints.cs`. |

## Данные и фоновые процессы

- `AppDbContext` содержит сущности пользователей/ключей/должностей, сохранений Xoxi, календаря и журналов доставки, подписок Web Push, модульных уведомлений, наград, кино, голосований и обеих игр. Большинство таблиц используют EF-конвенции; `xoxi_saves` настроена отдельно. Важные уникальные ограничения: сохранение Xoxi на пользователя; уведомление календаря на событие/дату; доставка на событие/подписку/дату; модульное уведомление на пользователя/модуль/источник; бюллетень на опрос/пользователя/вариант; участие в игровой комнате на комнату/пользователя.
- `BirthdayCalendarBackgroundService` запускает обновление прошедших системных дней рождения при старте и затем примерно раз в сутки. `BirthdayCalendarService` удаляет прошедшие записи и создаёт следующую дату для затронутых негостевых пользователей. Первичное заполнение всех дней рождения предусмотрено админским `/sync-birthdays`.
- `CalendarEventNotificationBackgroundService` вызывает `CalendarEventNotificationService` в интервале 09:00–23:00 по Москве с почасовой проверкой. Создаются уведомления за день до события и в день события. Для каждого негостевого пользователя добавляются записи `UserModuleNotification` с ключом `CalendarScene`; Web Push идёт по веб-подпискам. `CalendarEventPushDelivery` предотвращает повторную успешную отправку той же подписке за дату проверки, а неуспешные отправки повторяются.
- Опросы используют ключ модуля `VoteModule` и источник `vote:{id}`. Web Push требует VAPID; `WebPushSenderService` возвращает `false`, если настройки отсутствуют или отправка закончилась `WebPushException`.
- Push-подписка браузера при повторной регистрации переносится на текущего пользователя: один endpoint не должен оставаться привязанным к нескольким аккаунтам. Для мессенджера Web Push требует настроенных VAPID-ключей и разрешения уведомлений в браузере; без подписки сервер сохраняет непрочитанные, но не отправляет браузерное уведомление.
- Для новых временных правил учитывайте существующее различие: большинство меток времени — `DateTime.UtcNow`, календарный день рождения рассчитывается по UTC, а рассылка календаря и дата окончания голосований — по `Europe/Moscow` через `CalendarNotificationTime`.

## Практика изменений

1. Найдите нужный `Map...Endpoints()` в `Program.cs` и прочитайте соответствующий файл целиком вместе с DTO, моделью и конфигурацией в `AppDbContext`.
2. Сохраняйте действующий контракт: имена путей, JSON-поля, поведение JWT/admin key, фильтрацию по текущему пользователю и правила дат. Не предполагайте единую глобальную политику доступа — правила сейчас реализованы на уровне конкретных endpoints.
3. При изменении схемы создайте миграцию EF Core и проверьте её эффект на PostgreSQL. Не запускайте приложение против рабочей БД ради одной проверки компиляции: старт автоматически применяет миграции и включает фоновые службы, способные отправлять push.
4. После правок выполните `dotnet build PushPelmesh.sln`; для поведенческих изменений проверяйте конкретный HTTP-сценарий и БД отдельно. Если тестов ещё нет, добавляйте их для значимой логики, особенно прав доступа, дат, голосования и правил игр.
5. Не коммитьте локальные конфиги, JWT/admin/VAPID-ключи и реальные персональные данные. `ppadmin.html` сохраняет admin key в браузерном `localStorage`; учитывайте это при изменении страницы.
